# Korean Context v0.2 실전 품질 검증 설계

**상태:** 사용자 문서 검토 대기

**작성일:** 2026-09-04

**대상 릴리스:** `v0.2.0` 공개 프리릴리스

**상위 정본:** `ROADMAP.md`

## 1. 목적

Korean Context v0.2는 실제 저장소에서 발견한 복잡한 한국어 문제를 바탕으로 품질을 검증한다. 공개 저장소에는 익명화하고 최소화한 고정 평가 세트만 포함하며, Offen 전체 저장소 검사는 로컬 보조 증거로 분리한다.

v0.2가 답해야 할 핵심 질문은 다음과 같다.

> Korean Context가 강한 Codex 기준선보다 실제로 나은 결과를 만들면서 기술적 의미, 프로젝트 용어, 출력 형식과 이미 자연스러운 한국어를 일관되게 보존하는가?

## 2. 범위

### 포함

- 기존 v0.1 평가 100건의 회귀 검증
- Offen에서 파생한 공개 평가 60건
- 프로젝트 용어와 기존 문체 우선순위 검증
- 긴 산출물과 코드 식별자가 섞인 복합 사례
- Codex 기준선과 명시적 Korean Context 실행 비교
- 어려운 사례의 세 차례 반복 실행
- append-only 원본 실행 결과
- 자동 hard failure 검사와 수동 품질 채점
- 공개 재현 세트와 로컬 전체 저장소 스트레스 테스트 분리

### 제외

- Claude Code 어댑터
- 암시적 활성화 신뢰성 개선
- 범용 설치 프로그램과 npm 배포
- Gemini CLI 또는 다른 에이전트 지원
- 별도 LLM judge를 이용한 릴리스 판정
- Offen 원본 코드나 저장소 메타데이터 공개
- 기본 실행 경로의 추가 모델 호출

## 3. 고정 결정

- 공개 고정 평가 세트가 정식 v0.2 릴리스 게이트다.
- Offen 전체 검사는 실제 복잡도를 확인하는 로컬 보조 증거다.
- 프로젝트 용어와 기존 산출물 문체는 Korean Context 기본값보다 우선한다.
- v0.2는 품질을 분리해서 측정하기 위해 명시적 스킬 호출을 주 비교 대상으로 사용한다.
- 암시적 활성화는 v0.3 Claude Code 어댑터 단계에서 두 에이전트에 대해 함께 평가한다.
- 기존 v0.1 데이터와 스키마는 과거 결과 재현을 위해 그대로 보존한다.
- 표현의 다양성은 허용하지만 기술적 판단과 보존 조건의 변동은 허용하지 않는다.

## 4. 공개 평가와 로컬 검사의 경계

```text
Offen 실제 저장소
        │ 읽기 전용 검사
        ▼
로컬 후보·전체 문맥 테스트 ── 원문과 경로는 저장소 밖에만 보관
        │
        ├─ 통계·실패 유형 → 로컬 보조 증거
        │
        └─ 사람이 익명화·최소화
                    ▼
       공개 고정 평가 fixture
                    │
        baseline / Korean Context
                    ▼
          자동 검사 + 수동 채점
                    ▼
           재현 가능한 v0.2 보고서
```

공개 fixture에는 문제를 재현하는 데 필요한 최소 문장과 문맥만 포함한다. Offen의 절대 경로, 저장소 이름, 브랜치, 커밋 SHA, 내부 식별자, 고객 정보와 업무 데이터는 포함하지 않는다.

로컬 검사 결과는 `.local/evals/v0.2/`에 저장하고 Git에서 제외한다. 공개 보고서에는 집계 수치, 실패 유형과 공개 fixture로 재현 가능한 사례만 기록한다. 로컬 검사만 통과하고 공개 고정 세트가 실패하면 릴리스하지 않는다.

## 5. 공개 평가 세트

기존 v0.1 100건에 신규 60건을 추가해 총 160건을 검증한다.

| 유형                 | 수량 | 목적                                  |
| -------------------- | ---: | ------------------------------------- |
| 어색한 표현 개선     |   20 | 실제 UI, 주석과 Git 산출물 표현 교정  |
| 자연스러운 표현 보존 |   10 | 불필요한 재작성 측정                  |
| 프로젝트 용어 충돌   |   10 | 프로젝트에서 승인한 용어 우선 적용    |
| 긴 복합 산출물       |   10 | 여러 문단, 코드와 식별자 혼합         |
| 출력 형식 준수       |    5 | bullet, 커밋 제목과 표 형식 준수      |
| 일반 대화 경계       |    5 | 산출물이 아닐 때 개입하지 않는지 확인 |
| 합계                 |   60 | v0.1 100건과 함께 회귀 검증           |

프로젝트 용어 충돌 사례에는 `위젯`, `배치`, `칸`, `서랍`을 포함한다. 이 용어들은 일반적인 대안보다 프로젝트 관례가 우선한다는 사실을 검증하기 위한 예시이며 전역 기본 용어로 승격하지 않는다.

`evals/cases/v0.2/manifest.json`은 파일 목록, 유형별 기대 개수, 총 60건, 반복 대상과 schema version을 선언한다. 로더는 manifest에 선언하지 않은 JSONL 파일을 묵시적으로 포함하지 않는다.

## 7. v0.2 사례 스키마

v0.2 스키마는 기존 사례의 의미를 유지하면서 다음 필드를 추가한다.

```ts
type V02EvalCase = {
  schemaVersion: "0.2";
  id: string;
  kind: EvalKind;
  scenarioType:
    | "real-world-repair"
    | "preserve"
    | "project-conflict"
    | "long-artifact"
    | "format"
    | "boundary";
  surface: Surface;
  domain: Domain;
  input: string;
  expectedBehavior: string[];
  forbiddenBehavior: string[];
  protectedTokens: string[];
  protectedFacts: string[];
  expectedRegister: Register;
  projectVocabulary: {
    preferred: string[];
    accepted: string[];
    forbidden: string[];
  };
  requiredFormat: string[];
  provenance: "anonymized-derived" | "synthetic";
  sourceIds: string[];
  repeatCount: 1 | 3;
  privacyReviewed: true;
};
```

v0.1과 v0.2는 별도 Zod 스키마와 로더를 사용한다. 기존 100건을 형식만 맞추기 위해 변경하지 않는다.

## 8. 실행 식별과 결과 보존

하나의 실행은 다음 복합 키로 식별한다.

```text
suite + caseId + mode + attempt
```

v0.2 실행 결과에는 다음 메타데이터를 기록한다.

- Codex 버전과 모델
- 추론 수준
- Korean Context 버전
- 시작 시각과 종료 시각
- attempt 번호
- fixture와 prompt hash
- exit code
- 원문 출력과 stderr
- 완료, timeout, 중단 상태

`runs.jsonl`은 append-only 원본 기록이다. 실행기는 성공한 복합 키만 건너뛰며 실패 결과를 삭제하거나 성공 결과로 덮어쓰지 않는다. 최신 상태와 집계는 별도 파생 파일로 계산한다. 전체 결과 삭제는 명시적인 `--reset` 없이는 허용하지 않는다.

## 9. 비교 실행

신규 60건을 다음 두 모드에서 동일한 입력과 실행 조건으로 비교한다.

1. Korean Context가 없는 Codex 기준선
2. Korean Context를 명시적으로 호출한 Codex

가장 어려운 고정 20건은 각 모드에서 새 세션으로 세 차례 실행한다. 표현이 달라지는 것은 허용하지만 의미, 프로젝트 용어, 보호 대상과 필수 형식 판단은 모든 시도에서 같아야 한다.

Offen의 정규식 기반 검사기는 모델과 동일한 종합 점수로 비교하지 않는다. 탐지한 gold issue, 놓친 issue와 추가 경고만 집계해 의미 기반 검사와 정적 검사 사이의 범위를 설명한다.

## 10. 채점

v0.1과 비교할 수 있도록 기존 10점 체계를 유지한다.

- 자연스러움: 0~2
- 용어 정확성: 0~2
- 의미 보존: 0~2
- 산출물과 문체 적합성: 0~2
- 번역투 억제: 0~2

다음 항목은 평균 점수로 상쇄할 수 없는 별도 boolean 판정으로 기록한다.

- 프로젝트 용어 위반
- 보호 토큰, 사실, 숫자, 명령어 또는 키 이름 훼손
- 요구한 출력 형식 위반
- 입력에 없는 사실이나 조건 생성
- 자연스러운 원문의 불필요한 수정
- 일반 대화 경계 침범
- 기술적 의미 추가 또는 삭제

가능하면 채점자는 실행 모드를 가린 상태에서 평가한다. 경계선 판정은 두 번째 검토를 거치고 근거를 `notes`에 기록한다. LLM 채점은 참고 분석에는 사용할 수 있지만 릴리스 판정에는 사용하지 않는다.

## 11. 자동 검사와 수동 평가

자동 검사는 다음 항목을 담당한다.

- 스키마, 파일 목록과 유형별 수량
- ID와 실행 복합 키 중복
- 보호 토큰과 필수 문구
- 금지 용어와 출력 형식
- 실행 횟수와 버전 일관성
- 절대 경로와 private provenance 패턴
- 빈 출력, timeout과 중단 상태
- hard failure 집계

수동 평가는 자연스러움, 실제 의미 보존, 문체와 독자 적합성, 번역투 개선과 기준선 대비 실질적 개선을 담당한다.

## 12. 오류 처리

다음 조건에서는 평가를 통과시키지 않는다.

- 필요한 반복 실행이 하나라도 누락됨
- 한 비교 세트에 서로 다른 모델이나 플러그인 버전이 섞임
- 보호 대상 또는 프로젝트 용어 조건이 필요한 사례에 해당 정보가 없음
- 공개 fixture에 절대 경로나 private repository 흔적이 있음
- 빈 출력, timeout 또는 중단된 실행
- 수동 점수에 대응하는 원본 실행 결과가 없음

실행이 중단되면 완료된 원본 결과를 보존하고 다음 실행에서 이어간다. 실패를 정상 결과로 압축하지 않으며 요약 생성 단계가 불완전한 원본 세트를 통과시키지 않게 한다.

## 13. v0.2 릴리스 게이트

- 기술적 의미 훼손: 0건
- 프로젝트 승인 용어 위반: 0건
- 보호 토큰, 사실, 숫자, 명령어와 키 이름 훼손: 0건
- 입력에 없는 사실 또는 조건 생성: 0건
- 자연스러운 문장 불필요 수정: 5% 이하
- 요구 형식 준수: 95% 이상
- gold awkwardness 교정: 90% 이상
- 반복 실행의 심각한 실패 변동: 0건
- 기존 v0.1 100건의 중대한 회귀: 0건

하나라도 실패하면 `v0.2.0`을 배포하지 않는다. 실패 사례는 가장 좁은 회귀 평가부터 추가하고 규칙을 수정한 뒤 전체 고정 세트를 다시 실행한다.

## 14. 구현 단위

### A. 사례와 manifest

`src/eval`에 v0.2 스키마와 manifest 로더를 추가한다. 기존 `EvalCaseSchema`와 `loadEvalCases()`의 v0.1 동작은 유지한다.

### B. append-only 실행기

현재 case ID 단위로 최신 결과만 남기는 동작을 v0.2 실행에는 사용하지 않는다. v0.2 실행기는 복합 키로 재개하고 원본 실행을 보존한다. 요약기는 append-only 결과에서 비교 가능한 실행만 선택한다.

### C. 자동 hard failure 판정기

스키마에 선언된 보호 조건과 결과를 비교해 결정적인 실패를 자동 판정한다. 자연스러움처럼 문맥 판단이 필요한 항목을 정규식으로 억지 자동화하지 않는다.

### D. 개인정보 검사

공개 사례, fixture와 결과를 대상으로 Windows, WSL과 POSIX 절대 경로, Offen 저장소 식별자와 금지한 provenance 형태를 검사한다. 탐지되면 CI를 실패시킨다.

### E. 보고서

보고서는 기준선 대비 개선, 악화, 동일 결과와 hard failure를 분리한다. 작은 표본과 수동 채점, 모델 변동성, 로컬 검사 비재현성을 제한 사항으로 명시한다.

## 15. 테스트 전략

- 스키마는 유효·무효 사례를 모두 검사한다.
- manifest는 누락 파일, 잘못된 수량, 중복 ID와 선언되지 않은 파일을 거부한다.
- 반복 실행기는 `caseId + mode + attempt`별 재개와 실패 보존을 검사한다.
- 결과 집계는 버전 혼합, 누락된 attempt와 빈 출력을 거부한다.
- 개인정보 검사는 Windows, WSL과 POSIX 경로 fixture로 검증한다.
- hard failure 판정기는 보호 대상, 프로젝트 용어, 형식과 허위 사실 조건을 각각 독립적으로 검사한다.
- CI는 deterministic 검사만 수행하고 실제 모델 실행은 수동 릴리스 게이트로 유지한다.

## 16. 구현 및 릴리스 순서

2. 버전별 로더

4. 자동 hard failure 판정기
5. 익명화와 개인정보 검사
6. 공개 60건 fixture 작성과 검토
7. Offen 로컬 전체 검사
8. Codex 기준선과 명시적 실행
9. 수동 채점과 집계
10. 실패 기반 회귀 사례와 최소 규칙 수정
11. 전체 160건 검증
12. 보고서, 지원 표와 `ROADMAP.md` 갱신
13. 모든 게이트 통과 후 `v0.2.0` 프리릴리스

## 17. 완료 조건

v0.2는 공개 60건, 기존 100건, 원본 실행 결과, 수동 점수, 자동 hard failure 집계와 제한 사항이 모두 저장되고 13절의 릴리스 게이트가 전부 통과해야 완료된다. 로컬 Offen 검사는 결과를 보강하지만 공개 평가 실패를 덮을 수 없다.
